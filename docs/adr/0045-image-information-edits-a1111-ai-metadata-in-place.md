# Image Information Edits A1111 AI Metadata in Place

Image Information shows the AI Metadata of an image in an ordinary section of its own, between the Color and Camera sections: the generator, where the data is stored, the prompt, the negative prompt, the settings and the raw text. The section is always shown, laid out like the other sections, and is disabled when the image has no AI Metadata, as the Exif sections are without Exif; no other row is hidden for it. Prompt, Negative prompt and Settings are editable only when the AI Metadata is Automatic1111-style (Automatic1111, Forge, SD.Next) and stored in a PNG's `parameters` text chunk or in the Exif UserComment of a JPEG or WebP. Everything else shows read-only: ComfyUI, NovelAI and InvokeAI data, data hidden in the pixels, the JPEG comment segment, a UserComment in any other format, and the Generated with, Stored in and Raw boxes. An edit follows ADR-0044: it writes to the file the window shows, through `CommitAsync`, and the window then reads that file again.

- **Three boxes, composed again.** A commit composes the A1111 text from the box edited and the other two fields as the file holds them: the prompt, a `Negative prompt:` line when there is one, then the settings line, with `\n` line endings, as A1111 writes. A box is multi-line: Enter adds a new line, and the edit commits when the box loses focus, on Ctrl+Enter or on Tab. A value equal to what the file holds writes nothing.
- **An edit that would not read back is refused.** The composed text is parsed again with the reader's rules before it is written. If that does not give back the same three fields, such as for a prompt line starting with `Negative prompt:`, Settings that are not `Key: value` pairs, or all three boxes cleared, nothing is written and the box goes back to the file's value. So an edit can never remove the AI Metadata or move text to another field. Removing it stays with Remove metadata.
- **A PNG keeps every other byte.** `PngTextChunkWriter` replaces the first text chunk whose keyword is `parameters` in its own position, with a new CRC, and copies every other chunk byte for byte. Text that fits Latin-1 is written as `tEXt`, anything else as uncompressed UTF-8 `iTXt`, as PIL and therefore A1111 does; a `zTXt` source is written back as one of those two. A PNG it cannot parse (bad signature, a bad CRC on the chunk it replaces, no `IEND`) is refused. A PNG is never encoded again.
- **The UserComment carries its character code.** The comment is written as the 8-byte code `ASCII\0\0\0` with ASCII text when the text is all ASCII, and otherwise `UNICODE\0` with UTF-16 text, or UTF-8 for an Exif 3.0 profile, which is what `ExifReader` decodes. The old writer wrote ASCII bytes with no code, which turned a non-ASCII prompt into `?`.
- **A JPEG never falls back to encoding; a WebP is encoded.** A JPEG UserComment edit goes only through `JpegMetadataWriter`'s in-place rewrite. A JPEG it cannot parse, or Exif larger than one 64 KB segment, which a long non-ASCII prompt in UTF-16 can reach, is refused and left byte for byte as it was. A WebP has no segments to rewrite, so it is encoded again, as every other WebP tag edit is (ADR-0044).
- **One tag, two editors.** The Comment row stays shown and editable for every image. When the UserComment holds the AI Metadata, its label reads "Comment/Prompt", built from the Comment and Prompt translations and following a language change (ADR-0036), so it is plain that the Comment box and the AI Metadata boxes edit the same tag. Each editor reads the file again after its write, so the other one shows what was written.
- **The scan shows in Stored in.** While the pixels of a PNG or WebP with no stored AI Metadata are scanned for hidden data, the Stored in box says so. It shows the storage found, or nothing, when the scan ends, and the value of the image shown next when the scan is cancelled.

## Considered Options

- **One raw box holding the stored `parameters` text.** Simple and exact, but a typo fix could break the `Negative prompt:` marker or the settings line, and other tools would then read the data wrongly.
- **Merging the fork's `sd-metadata` branch.** It brought the bottom bar Image info button, a shell thumbnail change and Save As conflicts that would each have had to be undone, and it was written before ADR-0044's `CommitAsync` and the Image Information layout. Its reading and display were ported by hand instead.
- **The section above the file information, with the photo rows hidden while AI Metadata is shown.** This was the fork's layout. Its rows put the label above a box of their own width, so they ignored the window's responsive row sizing, and hiding rows inside a wrap panel shifted the row pairs, once leaving Software with no box. An ordinary section hides nothing and lines up with the rest.
- **Hiding the Comment row when the UserComment holds the AI Metadata,** so one tag has one box. It made the window's rows depend on the image, and the label says the same thing without hiding anything.
- **An overlay to read and edit a long field.** The full-width multi-line boxes, as wide as the Comment box, hold a long prompt well enough, and an overlay needed its own commit, focus and image-change rules.

## Consequences

- An edit of ComfyUI, NovelAI or InvokeAI data, or of data hidden in the pixels, needs a writer of its own; none of these formats is composed again.
- An image with no AI Metadata cannot get any from Image Information. The section shows for it, disabled and empty.
- A lossy WebP loses a little quality on each AI Metadata edit, as on every other WebP tag edit.
- An edit in the Comment box of an A1111 JPEG or WebP is an ordinary Comment edit: it writes the text as typed, and the AI Metadata boxes then show what the file holds. It can turn the UserComment into text that no longer reads as AI Metadata, which disables the section.
- A Settings edit is refused unless it starts with a settings line (`Steps:`, or at least two `Key: value` pairs). A cleared Settings box would otherwise compose a text that still reads back, only without its settings line, so the seed, sampler and model would be written out of the file.
- Edits run one at a time, each composed from what the file holds after the one before it, and each belongs to the image shown when it was committed. One still waiting when another image is shown is dropped, not written to that image.
- Reading the shown image's file again, as after PicView's own write, leaves a box alone when its field did not change in the file, so text being typed in another box is kept.
- A PNG `Comment` or `sd-metadata` chunk counts as AI Metadata only when it looks like it (`Steps:`, `Negative prompt:` or JSON), as a UserComment does, so an editor's comment such as GIMP's is not shown as a prompt.
