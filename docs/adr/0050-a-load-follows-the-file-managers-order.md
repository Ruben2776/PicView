# A Load Follows the File Manager's Order

With **Follow System Sorting** on, a Load that lists a folder first asks the platform's file manager how it shows that folder, and gives the **Listed Directory** that order (issue #328). On Windows the file manager is Explorer: a folder sorted by date modified, descending, in an open Explorer window is browsed in that order in PicView.

The seam is `IFolderOrderSource` (`PicView.Core/FileSorting`): `OrderOf(directory)` gives the `FileOrder` the file manager shows the folder in, or null. A platform offers one through `IPlatformSpecificService.FolderOrders`, which is null by default, and `AppLifecycle` gives it to the one `DirectoryOrders` (ADR-0048). On macOS the file manager is Finder (see On macOS). Linux offers none, so nothing is asked there.

`DirectoryOrders.FollowAsync(directory)` asks, off the caller's thread, and waits no longer than half a second. With an answer, a directory tabs already list takes that order and those tabs start sorting again; the answer is returned, and the Load lists in it and hands it to `TabViewModel.ListDirectory`, so a directory no tab listed starts with it. Without an answer the directory keeps the order it has, or starts with the **Default File Order**. So at a Load the order is, in turn: the file manager's, the directory's own, the default.

The Load asks where it lists: `TabLoad.ListAroundAsync` for a file and for a reload, `ListFolderAsync` for an opened folder, and `QuickLoad` where App Start lists before the tab's Load does (an opened folder, and Side-by-Side), which passes what it took in `LoadOptions.FollowedOrder`. A Load that steps to a file already in the tab's list lists nothing and asks nothing. An archive is never asked for.

Follow System Sorting is an App Setting, `Sorting.FollowSystemSorting` in the settings file, off by default, so a folder keeps the order PicView gives it until the user turns following on. It publishes its changes as `GlobalSettingsViewModel.IsFollowingSystemSorting` (ADR-0020). Turned on, `DirectoryOrders.FollowAllAsync` asks for every folder a tab lists now. Turned off, every directory keeps the order it has.

## On Windows

`ExplorerFolderOrder` (`PicView.Core.WindowsNT/FileSorting`) is the Windows source, offered by the Win32 app's platform service. It enumerates the shell's open windows (`IShellWindows`), and for each one whose folder view is on the directory reads the first sort column with its direction and the group column with its direction (`IFolderView2::GetSortColumns`, `GetGroupBy`). The folder a view shows is compared by its file system path, without case, so a search result, a library or another path to the same folder is not a match.

`ExplorerSort` turns what was read into a `FileOrder`, and is the part that is unit tested:

| Explorer column | File Order field |
|---|---|
| Name | Name |
| Size | File size |
| Date modified | Last write time |
| Date created | Creation time |
| Date accessed | Last access time |
| Date | Date |
| Type, Date taken and every other column | none: not followed |

Date (`System.ItemDate`) is the column a picture folder is sorted by unless another is chosen. Explorer shows in it the date taken of a file that has one, and else the earlier of its creation and last write time; a file with no usable time has no date and is listed first when ascending. The Date field of a File Order (`FileOrdering.DateOf`) gives the same: the date read from Explorer once it is read (ADR-0051), and until then what the file system says, the earlier of the two times, and no date, which goes before every dated file, for a file with either of them missing.

A view grouped by another column than it is sorted by, or with its groups in the other direction, is not followed, since the groups come first and no one field and direction gives that order. When several views show the folder, as two Explorer windows or two Explorer tabs do, the folder is followed in the order of the one the user sees and last used: the tab shown in the Explorer window that is furthest in front (`ExplorerSort.Followed`). A tab behind another in its window is passed over, and when the view in front is in no File Order the folder is not followed, as another window's order is not what the user sees. Only when every view of the folder is a tab behind another do they have to agree.

The interfaces are called through their vtables with function pointers. `IShellWindows` is an `IDispatch` interface, which source-generated COM does not declare, and function pointers need no marshalling code under Native AOT.

## On macOS

`FinderFolderOrder` (`PicView.Core.MacOS/FileSorting`) is the macOS source, offered by the macOS app's platform service. It reads two sources: Finder's open windows, asked over Apple Events, and the view Finder saved for the folder in the `.DS_Store` of the folder's parent. The windows say which one is in front, its view, and its sort where Finder's scripting has a word for it; the saved view tells what scripting cannot, which sort scripting has no word for and how the folder is grouped.

Finder is asked for its open windows: the folder each shows and its view, and of the first window that shows the folder, the sort column with its direction for a list view, or its arrangement for an icon view. Finder's scripting is the one source that is live and needs no more of the user than the Automation consent ("PicView wants to control Finder"). It was read on macOS 27: a click on a column header showed in the next answer, and an icon view sorted by Date Modified answered "arranged by modification date".

For a sort its scripting has no word for, Finder answers as if there were none: an icon view arranged by Date Added or Date Last Opened answers "not arranged", and a list view sorted by such a column answers the Name column, with the view's direction. Nor does it tell whether a view is grouped. Finder keeps a folder's view settings as records in the `.DS_Store` of its parent folder, under the folder's name, and these name every option: `GRP0`, a string, is what the folder is grouped by (`Date Last Opened`, `Kind`, `None`); `icvp`, a binary property list, holds the icon view's `arrangeBy` (`dateModified`, `dateLastOpened`, `dateAdded`, ...); and `lsvC`, or the older `lsvp`, holds the list view's `sortColumn`, with an `ascending` flag on each of its `columns`. The file does not say which view the folder is in, and it has no window in front to decide between two windows, so it is never read on its own: only for a folder a window shows, after the windows have been asked, on the same pool thread and only while the ask's half second has time left. `DsStore` reaches the folder's records through the file's own block table and tree, as the file also holds dead records, from earlier writes, that a scan for the name would find; `BinaryPlist` reads the two values of a property list that are needed. Every count, length and reference is checked against the bytes, and a file that is malformed, longer than 4 MiB, or holds nothing for the folder is no answer. The folder's name is matched without case and whichever way an accented letter is written.

| Finder sorts by | File Order field | Where it is read |
|---|---|---|
| Name | Name | scripting |
| Size | File size | scripting |
| Date Modified | Last write time | scripting |
| Date Created | Creation time | scripting |
| Kind | Extension | scripting |
| Date Last Opened | Last access time | saved view |
| Date Added, Tags, Comments, Version | none: not followed | saved view |

`FinderSort` turns what was read into a `FileOrder`, and is the part that is unit tested, with the saved view given as a `FinderSavedView`:

- A grouped view is followed by its group field, in any view and whatever scripting says of its sort, as the groups come first: a grouped column or gallery view is followed too. Date Last Opened, Date Modified and Date Created go newest first, Size largest first, Kind and Name ascending. A group with no field, as Date Added, Application, Tags, or a name not known, an empty one included, is not followed. `None`, which Finder writes when groups are turned off, and no record at all mean the folder is not grouped.
- A list view is followed by its column in Finder's direction, normal as ascending and reversed as descending. Where scripting answers Name, the saved sort column is looked at: Date Last Opened is followed as Last access time, in the direction of that column's `ascending` flag, descending when it has none; Date Added, Tags, Comments and Version are not followed; anything else leaves the Name scripting said.
- An icon view has no direction of its own. Finder sorts Name and Kind ascending, and Size and the dates descending, as Ruben checked against a window for each option. An icon view that answers "not arranged" is followed as Last access time, newest first, when its saved arrangement is Date Last Opened, and is otherwise not followed; snap to grid and arranged by label are not followed.
- A column or gallery view that is not grouped is not followed: scripting tells nothing of its sort.

Finder writes the saved view a little after a change. A saved sort that scripting would have named had it been current, as Date Modified, Date Created, Size, Kind, and Name for an icon view, is stale: Finder has not yet written what replaced it, and that cannot be told from the file. It is not used: a list view keeps scripting's answer, and an icon view that answers "not arranged" is not followed. Where the saved view gives nothing, as when the parent's file is missing or cannot be read, or the folder has no parent, the folder is followed as far as scripting alone goes. A file that is there but cannot be read is logged with `DebugHelper.LogDebug`; a missing one, the usual case, is not.

A Finder tab is a window of its own to scripting, and the windows come front to back, so the first one on the folder decides, as the view in front does on Windows. The folder a window shows is compared by its resolved path, without case and whichever way an accented letter is written; a search, a smart folder or a tag view is not a match.

Consent is asked for when the setting is turned on, so the prompt follows the user's own click, and never while the setting is off: `IFolderOrderSource.RequestAccess`, which only the macOS source answers with anything but yes (`AEDeterminePermissionToAutomateTarget`), is called before `FollowAllAsync` (`AppLifecycle.FollowFileManagerAsync`). A denial reads as no answer: the setting stays on, no folder is followed, and turning it on while denied shows one message, `FollowSystemSortingNotAllowed`, that points to System Settings, Privacy & Security, Automation. The saved view needs no consent, but it is read only for a folder a window shows, so a denial follows no folder by it either. An event never raises the question itself (`kAEDoNotPromptForUserConsent`), so a Load cannot bring it up at App Start or in the middle of browsing, as it otherwise would with the setting on and the consent undecided: a settings file carried to another Mac, or the setting turned on while Finder was not running. Until the user has allowed it, such an event fails, and the setting has to be turned off and on to be asked. `Info.plist` says why PicView asks, in `NSAppleEventsUsageDescription`, without which macOS refuses the events of a signed app.

macOS offers no `IFileDateSource`: Finder has no column like Explorer's Date, so no Finder column maps to the Date field, which stays the earlier of the two file system times there.

### Considered on macOS

- **Read the folder's saved view state from `.DS_Store` alone.** It needs no consent, works with Finder closed, and names every sort option and the grouping. It was first rejected partly as stale: the file of a folder whose sort had been changed twice in a day was still two weeks old. That reading was wrong. It was of the folder's own `.DS_Store`, which holds the views of the folders inside it; a folder's view is kept in its parent's file, and there a change of sort was in the file under a minute to two minutes later, the three times it was read. It is now the second source. On its own it would still not do: the format is undocumented, it does not say which view the folder is in, it has no window in front to decide between two windows, and its lag would apply to every sort and not only to those scripting cannot name.
- **Use the saved sort wherever it differs from scripting's.** Where scripting has a word for the saved sort, it would have said it had it been current, so a difference means the file is behind, and the saved sort is an order Finder no longer shows.
- **Leave a grouped view unfollowed, or follow it by its sort as before.** The groups come first, so the sort alone is not the order Finder shows, and a folder not followed is the larger bug. Ruben chose to follow it by its group field, which makes the saved view part of every ask and not only of those scripting cannot answer.
- **Read the column headers through Accessibility.** It would see every column. The user has to grant "control this computer" by hand in System Settings, and header names are localized.
- **Never follow an answer of Name**, as scripting answers it for a column it has no word for. The most common sort would then never be followed, and the saved view now tells those columns apart.

### Consequences on macOS

- Last access time is the file system's, which changes when anything reads the file, a backup or a preview included; Finder's Date Last Opened is when the user last opened it in an app. A folder followed by Date Last Opened can be in another order than Finder's.
- Extension order is not Kind order: Finder sorts by the kind's name in the system's language, and one kind covers several extensions. In a folder grouped by Kind, Finder put `.psd` first, as "Adobe Photoshop document", and `.jpg`, `.jpeg` and `.jfif` together, as "JPEG image"; the Extension field puts `.psd` near the end and keeps the three apart. Kind is followed so all the same, as nearly the same order is better than none (see Consequences, on Explorer's Type).
- The saved view lags behind a change: a change of sort was in the file under a minute to two minutes later, the three times it was read, and how short the lag can be was not measured. For that long a view just changed to Date Last Opened is a list view followed as Name, or an icon view not followed; a list view just changed from Date Last Opened or Date Added to Name is still followed as Last access time, or not followed; and turning groups on or off, or changing the group field, is not seen. Each rights itself at the next Load after Finder has written.
- Inside a group Finder orders by the view's sort. PicView has only the group field, so it orders by that field throughout, and files that tie on it, as the files of one extension do, by name (ADR-0039). The two can differ within a group.
- A folder whose parent's `.DS_Store` cannot be read, as may be so on a network volume or at a volume's root, is followed as far as scripting alone goes: a list view by its column, as Name where scripting has no word for it, an icon view by its arrangement, and no view as grouped.
- The group field is the string Finder writes, which looks to be a fixed English name. `Date Last Opened`, `Kind` and `None` were read from a real saved file; `Size`, `Date Modified`, `Date Created` and `Name` are names found in Finder's own binary, next to the others, and a view grouped by one of them was not looked at, so its name and its direction rest on that and on Finder's usual order. That the strings are not translated was not checked on a system in another language.
- Finder sorts names with its own localized comparison and PicView with `NaturalStringComparer`, so a folder followed by Name can differ from Finder where punctuation or accents decide.
- Finder is asked with Apple Events sent in-process (`AESendMessage`, as `NSAppleEventDescriptor.sendEvent` does). A prototype sent four of them, the folder, the view, the sort column and its direction, each of every Finder window at once, and was timed on macOS 27 with ten windows open, from a background thread while the main thread was blocked: 0.19 seconds for the first ask of a process and 0.07 after, well inside the half second a Load waits, which stays the same on every platform. One ask has half a second for all of its events together: each is given what is left of it as its timeout, and none is sent past it, so a slow Finder with many windows holds the pool thread no longer than that.
- From .NET the same ask took 30 to 90 milliseconds, read on a pool thread of the test host against ten open windows. The view of every window and the folder of every window are one event each, and the sort column and its direction, or the arrangement, are asked of the one window that is followed. With the saved view read as well, the first ask of a process took 236 to 259 milliseconds and later asks 85 to 91, against the half second a Load waits. Where Finder refuses the folders of all windows at once, as it may for a window that shows no folder on a disk (Recents, AirDrop, a search), each window is asked for its own, front to back and no further than the first that shows the folder, as no window behind it is followed; that path was not run against such a window.
- The Apple Event functions are called with `LibraryImport` and plain structures, the descriptor packed to two bytes as the headers declare it, so no Objective-C runtime call is made.
- The answers are four-character codes (`lsvw` and `icnv` for a list and an icon view; `elsn`, `elss`, `elsm`, `elsc` and `elsk` for the name, size, modification date, creation date and kind columns; `snrm` and `srvs` for the direction; `nama`, `mdta`, `cdta`, `siza`, `kina` and `narr` for an icon view arranged by name, modification date, creation date, size and kind, or not arranged), so nothing read depends on Finder's language. Each code was checked against Finder's own name for it.
- `osascript` was timed too: 0.46 seconds for the same four events, of which 0.05 is the process and 0.13 its first contact with Finder, and 1.2 seconds with a loop over the windows. Too near the limit.
- `NSAppleScript` in-process took 0.11 seconds on the main thread, but off it one ask timed out after two minutes with the main thread blocked, and took up to 0.67 seconds with it running. It is documented for the main thread only, where a slow Finder would hold the interface.

- Finder's normal direction is ascending and its reversed descending: a window sorted by Size that Finder told as reversed showed the largest files first. The date columns are taken to go the same way, which was not checked against a window.
- The item is shown wherever the platform offers a source: `GlobalSettingsViewModel.CanFollowSystemSorting` is `DirectoryOrders.CanFollow`, set with the services every tab shares, and the Action is listed for Windows and macOS. In the macOS native menu the sort items are disabled while following, as in the other menus.
- The message for a denial is in English in every language but Danish until it is translated.
- Tested with `FinderSortTests`, with windows and saved views given as data; `DsStoreTests`, with files laid out in the test; `BinaryPlistTests`, with property lists made by `plutil`; `FinderSavedFileTests`, for where the saved view is looked for and files written to a temporary folder; `DirectoryOrdersAccessTests`; and a refusal with a fake source in `AppLifecycleTests`. The live read was checked on macOS 27 from the test host, against windows Ruben set up: an icon view sorted by Date Modified, followed as Last write time, newest first; a list view sorted by clicking its Date Last Opened column, which scripting answered as Name and the saved view as Date Last Opened, descending, followed as Last access time with the most recently opened file on top, as Finder showed it; and a view grouped by Kind, followed as Extension, ascending. The consent prompt, a real denial, the built app, groups by Size, Date Modified, Date Created and Name, and a system in another language were not run.

## Considered Options

- **Take the literal item order of the Explorer view.** It would match Explorer for any column and any grouping. No `FileOrdering` reproduces such a list, so a created or renamed file could only be appended, as under Random, and a re-sort could not restore it (ADR-0039's guarantee). A `FileOrder` keeps inserts where a sort would put them, at the cost of the columns it has no field for.
- **Read the saved view state of a folder from the registry.** It would work with Explorer closed. The format is undocumented binary and could change with a Windows update; the live window is the documented way.
- **A sort field of its own, "Explorer", in the menu.** It would need a second field beside it for when Explorer has no answer. A setting leaves the sort menu as it is, and the menu's sort still works on top of it.
- **Follow the file manager's sort as it changes.** Explorer gives no cheap event for it, so it would be polled. The order is read once per Load, and a reload reads it again.
- **Make the file manager's order the Default File Order too.** One folder opened from a date-sorted Explorer window would then change how every other folder opens. Only a sort made in PicView writes the default.

## Consequences

- The file manager's order wins over a sort made in PicView earlier: opening another file from the folder, or reloading, asks again and re-sorts every tab on the directory. A sort from the menu then holds until the next Load that lists the folder.
- A menu sort writes to the Default File Order only what was chosen, the field or the direction (`DirectoryOrders.SortAsync`'s `asDefault`). Choosing Descending in a folder Explorer shows by size makes that folder size descending and the default's direction descending, and leaves the default's field as it was.
- Stepping to the next or previous folder is a Load that lists, so with an Explorer window on that folder the order can change, field and direction, from one folder to the next.
- The first image does not wait for the answer when it shows before the listing, which is every Load of one image. Where the Load lists first, an opened folder and Side-by-Side, the image waits for the answer, at most the half second.
- An ask that outruns the limit is left to finish on its pool thread, and the file manager is not asked again until it has, so a hung Explorer holds one thread and not one per Load. Loads meanwhile are not followed.
- Any failure of the source is logged with `DebugHelper.LogDebug` and reads as no answer.
- The answer is only as good as the source's mapping: a view the source cannot express as a `FileOrder` gives null, and the folder opens as if no window showed it.
- `LoadOptions.FollowedOrder` is the one way a caller that lists for the Load can pass the order on; files given without it are of a directory that starts with the default.
- `WindowSettingRecordReadsTests` lets `Sorting.FollowSystemSorting` be read anywhere, as `IncludeSubDirectories` is: both are App Settings of their own and not the Default File Order.
- Dates taken are read after the list shows, in the background, and the files sorted again where that changes their order (ADR-0051), as reading one through the shell costs about 3 ms a file.
- Date is a field like the others: `SortFilesByDate` is its Action, in the sort category of the keybindings, with an item in the sort submenus and the macOS native menu, labeled with the existing `Date` translation. It is 7 in `Sorting.SortPreference`, which a version from before it reads as Name.
- An archive's pages go by their entry's modified time under Date, as under the other date fields, and an extracted page's file, stamped with that time on its creation and last write time, has the same date.
- Explorer's Type column sorts by the type's name, so `.jpg` and `.jpeg` are one type; mapping it to the Extension field would give an order that is nearly Explorer's, which was taken to read as a bug, so it is left out. Finder's Kind sorts the same way and is followed on macOS as the Extension field, by a later rule of Ruben, the project's owner: nearly the same order is better than none, as a folder not followed and a folder followed almost right both read as a bug, and the second is the smaller one. Type was left as it is because Windows could not be run from the Mac Kind was built on.
- The views were first required to agree, which left a folder unfollowed whenever a second Explorer window or a forgotten tab showed it in another order, as the first real use found. The view in front wins instead. Telling it needs a call that only works from a single-threaded apartment (`IOleWindow::GetWindow`, which is input-synchronous), so `ExplorerFolderOrder` reads the views on a thread of its own in one, and it rests on undocumented behaviour: each Explorer tab has a `ShellTabWindowClass` window in its Explorer window, the first of which is the tab shown. Where that stops holding, every tab counts as shown and the window in front decides alone.
- Which window is furthest in front is its place among the desktop's top-level windows, so an Explorer window used last is followed though PicView was opened from elsewhere.
- Only the first sort column is read, and files that tie on it go by name, then by path (ADR-0039), which may not be how Explorer breaks the tie.
- The item is in the sort submenu of the main context menu and of the title bar menu, hidden where the platform offers no source (`GlobalSettingsViewModel.CanFollowSystemSorting`), and in the macOS native menu as well. `ToggleFollowSystemSorting` is its Action, with no default key.
- The other languages show the English text for the item until it is translated; Danish has its own.
- Tested with a fake `IFolderOrderSource`, and `ExplorerSort` with views given as data. `QuickLoad`'s two asks at App Start are not covered by a test.
- The live read was checked on Windows 11 from the test host, from a pool thread: against one Explorer window sorted by name and by Date, against two Explorer windows on one folder in different orders, each brought to the front in turn, and with the front one's tab put behind a new tab. Grouped views, an elevated PicView and the Native AOT build were not run.
