# A Tab Derives Its View

Which view a **Tab** shows, its **Tab View**, is derived by one private method on `TabViewModel` from the tab's own state: its Crop, its **Title Phase** and whether it shows anything. The rule is one: a crop is open (`Crop` is not null) means the crop control; otherwise the tab shows something, which is its `Model` having an image or a file, or its Title Phase is Loading or Downloading, means the image viewer; otherwise the start-up menu. A Single Image counts as showing something, since its model has an image; a Stand-in does not, since it changes only the `Image` bindable; a tab that lost its files shows an empty model and so derives the menu, as does a new tab, a Fresh Tab and a tab whose load failed with nothing shown, in the Error phase or not. The tab publishes the kind as a read-only bindable, `ViewKind` (a `TabViewKind` of `StartUpMenu`, `ImageViewer` or `Crop`), which starts at the menu and notifies only when the kind changes. The derive is called from inside the tab after each input changes: the `Crop` setter, `SetLoading`, `SetDownloading`, `SetError`, `EndLoading` (and so `ShowLoading`), and `Publish` after `Titles.OnShown`, which covers `Display`, `DisplaySingleImage`, `ShowPage` and `BecomeFreshAsync`. It runs on whatever thread changed an input, as the derive of Next/Prev does (ADR-0017), allocates nothing and reads no disk, so showing an image is never delayed.

The control the kind asks for is made by the Main Window, through one Core port. `ITabViewFactory.Attach(tab)` returns an `ITabViews`, whose `View` is the control the tab's window shows for it now, held by Core as an object. The window's `TabOverviewViewModel` takes the factory once, in `SetViewFactory`, called by `MainWindowLifecycle.Create` next to `SetHookups`, and attaches every tab already in it, every tab `CreateTabInternal` makes and every tab `Adopt` takes; `Detach`, which `MoveOut` and `Release` call, disposes the tab's views. A tab is attached whether or not it is initialized. The tab's `CurrentView` stays where its readers and the content binding find it, but is read-only: the tab follows the attached views' `View` and shows null once detached. The adapter, `TabViews` in `PicView.Avalonia/UI`, is one per Main Window. It subscribes to each attached tab's `ViewKind` and reacts on the UI thread, inline when it is already there and otherwise posted at Send priority, so the control is in place before any fit posted at normal priority; a posted reaction reads the kind as it is when it runs. It makes each control the first time its kind asks, with the tab as its `DataContext`: the viewer once per tab, kept, so a crop that opens and closes shows the same viewer again; the menu once per tab, kept, and fitted with `WindowFitter.FitStartUpMenu` every time it is shown, before it is set, so an unshown window still opens at the menu's size; and a crop control per crop, dropped when the kind leaves Crop. Releasing a tab disposes its viewer, drops the other two and sets its view to null. At start-up (ADR-0005) `MainWindowLifecycle.OpenAtAppStart` knows whether the window opens a source, the given one or the last file when no launch file may arrive and the setting asks, and `Create` then says Loading on the first tab before it attaches the factory, so the first kind the adapter sees is the viewer and no menu is made for that window. `QuickLoad.StartUpAsync` takes its own ticket at its start, which replaces the lifecycle's phase, and ends it when its result is not Loaded, which derives the menu.

Before this, sixteen writes in nine files assigned a control into `CurrentView`, a `BindableReactiveProperty<object?>` anyone could write. Loads switched the view by hand: `SourceOpener.OpenAsync` hopped to the UI thread to make a viewer when the view was null or the menu and made a new menu after a Failed outcome when it had been one, `QuickLoad` made a viewer in `LoadThroughCoreAsync` and again in `ShowImageViewerAndHookUpAsync`, and called `ViewChangeHelper.SwitchToStartUpMenu` on failure, `StartUpMenu.PasteClick` made a viewer before pasting, and `DragAndDropManager.Drop` made one before loading through `SwitchToImageViewerIfNecessary`. Three of them undid their own write when nothing showed: the opener, the paste and the drop, through `SwitchStartUpMenuIfNecessary`. The crop backed the view up and restored it: `CropService.StartCropControl` saved `CurrentView` in `_backUpView`, made a `CropControl` with the window's fitted sizes and assigned it, and `CloseCropControl` assigned the backup back, so `ImageViewer.DisposeGalleryViewWhenReplaced` followed `CurrentView` to dispose its gallery view once another view replaced it, with an exception for a crop control. Three patches covered a missing or detached view: `MainView.MainTabControlOnTabCreated` assigned a viewer or a fitted menu when a tab's container was created without one, `UpdateImage.SetSingleImage` made a viewer when the view was not one, and `MainWindow.RefreshViewBinding` re-set a moved view's `DataContext` to its tab, since the menu's came from the content template and was lost when the view left the window. `MainWindowLifecycle` made the start-up menu in `OpenNewAsync` and `ShowStartUpMenuOrLastFile` through `CreateStartUpMenu`, and `ViewChangeHelper` disposed the old view, assigned a new menu and wrote the loading indicator to false; `IActionRunner.ShowStartUpMenu` existed only so `BecomeFreshAsync` could reach it.

## Considered Options

- **The control leaves Core.** The tab exposes only `ViewKind`; the control lives in the window's adapter, a host control in the content template asks for it, and readers ask the window. The cleaner seam, but readers that hold only a view model today would need a way to their window, about 24 edits and one new lookup. Chosen instead: `CurrentView` stays on the tab, read-only and fed through the port, as `Hookups` and `CropService` are already UI things the tab holds opaquely.
- **A pull port, `ViewFor(tab, kind)`, called by the tab's derive.** Core would derive `CurrentView` itself, but the derive runs on the loading thread and a control can only be made on the UI thread, so the factory would have to make every control ahead of need or post and call back. Subscribing on the adapter puts the one hop where the thread boundary is.
- **A public setter the adapter uses**, `tab.ShowView(control)`. One line, but a writable door is how sixteen writes accumulated. The port hands the tab an observable it reads; no public method takes a control.
- **The menu sizes itself in `OnAttachedToVisualTree`.** It covers a menu that comes back, but the first attach of a new window's menu happens after `Show()`, past `FitStartUpMenu`'s unshown-window branch, so an AutoFit window would open at its default size. The adapter fits before it sets the view, every time, on the UI thread it is already on.
- **Both controls made at attach**, so a kind change never makes one. Every tab opened with a source would make a menu it never shows, which the start-up path cannot afford; making each control the first time its kind asks costs the same hop and nothing extra.
- **`IsFresh` as an input** instead of whether the model shows something, the review's wording. A pasted Single Image shows in a tab that was never initialized, so freshness alone would show it the menu; an empty model covers both the never-opened tab and the one that lost its files.
- **The viewer moves with the tab** between windows, as the control object did with a `DataContext` patch. Then the adapter would be per tab, not per window, and the menu's fit would need the window found from the tab; a move is rare, and the new window's viewer rebinds to the tab's state.
- **`ViewKind` as a reactive combine** over `Crop`, the phase and the model. Neither the Crop nor the model is observable, so it needs the manual trigger anyway, as ADR-0017 found for Next/Prev.

## Consequences

- A new way to change which view a tab shows is an input to the rule, a derive call inside the tab, never a view write. An assignment to `CurrentView.Value` outside the tab does not compile.
- `ITabViewFactory` is the one way a control reaches a tab. The tab's `SetViews(ITabViews?)` is internal and called only by its `TabOverviewViewModel` at attach and detach; it subscribes to the attached views' `View` and sets a private bindable, rather than an R3 `Switch` over a bindable of views, since the tab's primary constructor has no body to build the chain in.
- R3's `IReadOnlyBindableReactiveProperty<T>` exposes `Value`, not `CurrentValue`, so every reader that wrote `CurrentView.CurrentValue`, in fifteen files, now writes `CurrentView.Value`, one token each. The paths they read are otherwise the same, and readers that ask only whether the tab shows the viewer may read `ViewKind` instead.
- A failed load undoes nothing: it ends its Loading ticket, and the tab derives the menu when it shows nothing. `SourceOpener` no longer hops to the UI thread before a load begins. `ViewChangeHelper` is deleted, with its indicator write, which nothing replaces, since the loading indicator derives from the active tab's Title Phase (ADR-0019). `IActionRunner.ShowStartUpMenu`, its mapping and its recording in the tests are deleted, and `BecomeFreshAsync` derives the menu through its `Display` of an empty model. The FileWatcher tests that awaited that action await `ViewKind` and the shown file being cleared.
- The crop saves and restores nothing. `CropService` keeps `IsCropping`, its commands, the `Crop` set and the `Refit` after it; the control is the adapter's. Since the adapter makes it the moment `Crop` is set, before the service's refit, `CropControl.axaml` binds its `Width` and `Height` to the window's `ImageWidth` and `ImageHeight` and sets its `Margin` to 0, and follows the fit.
- Each control is made once per tab per window and disposed when the tab leaves: `ImageViewer.Dispose` disposes its `GalleryView`, and `DisposeGalleryViewWhenReplaced` is deleted. A tab moved to another Main Window gets a new viewer there, which rebinds to the tab's state; a playing motion photo stops at the move. `MainView.MainTabControlOnTabCreated` and `MainWindow.RefreshViewBinding` are deleted.
- The adapter hops to the UI thread; a tab's Load never waits for it. The adapter subscribes and the tab never calls into it, so a load that says Loading on a thread-pool thread returns at once and the viewer appears on the UI thread with or before the image. A tab created on a thread-pool thread, as the consecutive pasted files are, has its control one hop later. The adapter does not coalesce a burst of off-thread changes: each posts its own job, and each reads the kind as it is when it runs, which is correct and wasteful. Coalescing them is a follow-up, not a rule.
- `DeriveViewKind` returns early when the tab is disposed, since a load may end after its tab closed, as `Publish` does.
- ADR-0005 holds: the window, then the image, then navigation, and the viewer still exists before the first image shows. The lifecycle says Loading at creation for a window that opens a source, so the viewer is made in `Create`, before `Show()`, where `QuickLoad` made it in the same dispatcher step as `Show()`. `ShowImageViewerAndHookUpAsync` is `HookUpAsync`, and `OpenNewAsync` and `ShowStartUpMenuOrLastFile` show the menu the adapter made and fitted at creation; `CreateStartUpMenu` is deleted.
- ADR-0014 holds: the tab's shown state has one writer, and its view one derivation. `UpdateImage.SetSingleImage` keeps its refit and centering for a tab whose viewer the adapter is making; the adapter's Send-priority reaction runs before them. `WindowFitter` is unchanged, and `FitStartUpMenu` gains one caller, the adapter.
