# A Tab's Load Has One Owner

Each **Tab** holds one module, `TabLoad` in Core, reached as `tab.Load`, that owns every **Load** of the tab: it takes the load version, takes the mark from the tab's **Archive Openings** (ADR-0013), makes the tab's iterator when it has none, says Loading, shows the image, lists the files around it, watches their folder, primes the cache, reports which opening is shown, and publishes whether the tab is loading. Its one entry, `LoadAsync(source, options)`, takes a **Source** as text and decides whether it is a file, a folder, an archive or a URL; the options are a root directory for subdirectories, an archive entry, a relist flag, and an already decoded model for the startup path. It returns Loaded, Failed with a reason, or Superseded, and completes only once the image shows, a newer Load supersedes it, or it fails (ADR-0012), from any thread, never waiting for the UI thread. The **Title Phase** Loading is versioned: a Load enters it with its version and only that version's end, or the next shown image, leaves it, so a load that gives up late never ends a newer one's phase; the iterator's slow step holds a ticket the same way. The shared services a Load needs (the image cache, the thumbnail cache and loader, the folder watcher, the image loader, the string comparer) are composed once at App Start (ADR-0007) and handed to every tab at creation.

Before this, the protocol was written by hand five times in `NavigationService`: begin a version, take a mark, check the version at up to six points, report Shown; its interface had fifteen members and one adapter, `TabOverviewViewModel` forwarded five load entries and selected a tab nothing asked it to, and seven callers went around `SourceOpener`, redoing its work (a new image viewer, the indicator, Loading) or skipping it. The Loading phase had five writers in five files, `ImageIterator` among them, and Core wrote the Main Window's loading indicator through `tab.ParentWindowContext`. `TabNavigationInitializer` held a second copy of the start of the protocol for the startup path, composed the navigation services lazily on the first open of any tab, and recreated the iterator for a tab that had shown a Single Image.

## Considered Options

- **A shared Load module**, constructed once with the services and given the tab per call, as `NavigationService` is: the version, the mark and the phase are the tab's facts, so the protocol would still read and write the tab from outside, and "this tab's current load" would stay a mechanism on the tab and a protocol elsewhere.
- **One entry per kind of Source** (file, folder, archive, URL): every caller holds a string and would resolve the kind itself, which `SourceOpener`, `QuickLoad` and `LoadFromStringAsync` already did three times.
- **An unversioned Loading phase**, with the Load as its only writer for loads: the iterator's step says Loading too, and ADR-0015 recorded that a late end could leave a newer phase wrong. A ticket is one int on the phase.
- **Two entries for startup**: `QuickLoad` keeps calling `Display` and the Load gets "the image is shown, attach its files". It keeps a second hand-written start of the protocol, which is what `TabNavigationInitializer.Initialize` was.
- **Composing the services lazily**, as before, so the first image shows sooner: constructing them is cheap, and listing files is what waits (ADR-0005), so App Start composes them and the first image shows as before.
- **The Load owns the tab's cancellation** and hands out tokens: 27 sites receive the live source today, and the version already supersedes a load; changing the handout is its own slice.

## Consequences

- A new way to load a Source is an option on `LoadAsync`, never a new entry or a new protocol. A load that bypasses the Load never says Loading, never marks and never lists, so it shows as such.
- `SourceOpener` stays the UI adapter around the Load: the start-up menu, the error tooltip, the hover bar, the Center. It gains a tab parameter, so a consecutive pasted file opens into its tab through it. Every UI caller goes through it; Core callers, such as the Resize window's conversion, call the tab's Load.
- `QuickLoad` keeps ADR-0005's order to the millisecond: it pings, sizes and shows the window, makes the viewer and hooks the tab up, and hands the Load the decoded model. `TabNavigationInitializer` keeps only the UI side of a first open.
- The Main Window derives its loading indicator from the active tab's `IsLoading` and a hidden titlebar, for every Load: the titlebar already says Loading, so the indicator earns its place only without it. The other writers of the indicator are unchanged and are the next slice's.
- `INavigationService` loses its six load entries and `RepopulateIterator`, and keeps stepping, sorting, next folder and next archive. `TabOverviewViewModel` loses its five load forwards; its navigation forwards stay.
- ADR-0012 holds: a step Back or Forward ends when its Load completes, which is once the image shows. ADR-0013 holds: the mark and Shown are written once, inside the Load. ADR-0014 holds: `Display` stays the tab's method and the Load calls it. ADR-0015's parked owner of the Loading phase is this module.
- The 28 load tests move to the Load's interface and leave `NavigationServiceTests`, which keeps the sort test. `SourceOpener` stays covered by the headless lifecycle tests.
