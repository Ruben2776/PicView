# PicView Shows the File It Rewrote

The **Shown File** is shown again after PicView rewrites or replaces it, and the tab's turn and effects are reset when they were written into the file; a replace never overwrites another file; before PicView overwrites a file it recycles a copy where the temp folder's drive has a Recycle Bin and the recycle goes through, and otherwise logs that it wrote with no backup; the original a replace removes goes to the Recycle Bin where its drive has one; every in-process write of a tab's shown image goes through one save module, `ShownFileWriter` in `PicView.Core/Saving`.

A writer (Save, Save As, Crop, the Resize dialog, rename to another extension, the Convert window, the Info-window resize, Optimize) describes a job: the source, the changes and the destination. The module reads the source, writes off the UI thread with the tab Busy and one write at a time per tab (a second write reads the turn after the first one's reshow reset it), and picks the follow-up by the destination, so no writer touches the cache, the tab's Orientation, `FileRenames`, the tab's load or deletes the original itself.

- **Over itself.** The tab shows the file again through `ShowRewrittenAsync(turnApplied)`: the cached image and the gallery thumbnail are forgotten, the file is decoded again and shown in place, keeping the Side-by-Side pair and the page. The turn is reset when it was written into the file, and the effects, when the Effects Render was written, are reset with `EffectsViewModel.DiscardEffects` on the UI thread. A save that changed nothing (no turn, no effects, no edits), Convert's "No conversion" included, writes nothing: no encode and no Recycle Bin copy. It keeps the shown model and only forgets the cached image and thumbnail.
- **Replaces the original.** The new path replaces the original: histories follow (`FileRenames.Follow`), the tab loads the new file, then the original is removed, so the watcher removes a file that is no longer shown. On a drive with a Recycle Bin the original goes there; when recycling it fails, as when the user refuses the shell's "delete permanently?" for a file too large for the bin, the original is kept beside the new file and the failure is logged. Only on a drive with no Recycle Bin is it deleted. A replace never overwrites another file: when the name is taken nothing is written or deleted, and the writer shows the "file already exists" tooltip.
- **Copy elsewhere.** Nothing changes in the tab. A copy onto the Shown File itself counts as over itself.
- **The source** is chosen by the writer from two kinds. The Save Source (Effects Render, else the file, else the pixels of a Single Image, with the turn and flip) for Save, Save As, Resize, the Info-window resize, Convert and rename to another extension; the file on disk for Crop (ADR-0028) and Optimize.
- **A Single Image has no file**, so over itself and replace become Save As for Save, Resize and Convert, which then work on a pasted image. The Info-window resize does nothing for a Single Image.
- **Recycle Bin Backup.** Before the module writes over a file that exists, it copies that file in PicView's temp folder and recycles the copy quietly from there (`RecycleQuietlyAsync`: no confirmation, no error dialog, no "delete permanently?" question), so the folder watcher sees no extra file and a plain Save asks nothing. Whether there is a bin is asked of the temp copy's drive. The Recycle Bin's Restore therefore puts the copy in the temp folder, not beside the original. When the temp folder's drive has no Recycle Bin, or the copy or its recycle fails (on Windows a copy too large for the bin is deleted without asking), there is no backup: the failure is logged, the copy, if made, is left for the temp cleanup, and the write goes ahead. The step carries a TODO for a future Undo/Redo, which should restore from this copy.
- **Writes encode to the system temp folder and then copy to the destination**, never to a temp file in the watched folder, which the folder watcher would see, and a failed encode leaves no partial file there. The copy over an existing file is not atomic, and the Recycle Bin copy is the net.
- View-model tooltip messages (`TooltipHelper.ShowTooltipMessage(vm, ...)`) show in the Main Window: each follows its `ToolTipMessageSource`. They were silently dropped before, rename's included.
- With "reset zoom on change" on, any showing of the file resets the turn, as before, so an Optimize or another write that did not write the turn still loses it then.
- The crop of a Single Image goes through the module too, as a copy: its pixels come through the Single Image seam, the picker suggests a new PNG, and a picked file that exists gets the Recycle Bin Backup.

## Considered Options

- **A Core module with one seam.** A writer builds a job; the module in `PicView.Core` reads, changes, writes and follows up by destination. Only a Single Image's pixels, an Avalonia `Bitmap`, come through a small interface implemented in `PicView.Avalonia`. The Resize and Info view models already live in Core, and the tests stay plain xUnit with a fake source. A module that only forwarded callbacks, with each writer encoding through its own `MagickImage`, would have left the drift between writers where it was.
- **Grow `FileSavingService` in Avalonia.** Less code moves, but the Core view models would need an interface to reach it anyway, and its tests need headless Avalonia.
- **Every writer reads the Save Source.** The most uniform, but Crop would pick up effects, against ADR-0028, and Optimize would stop being lossless.

## Consequences

- `Cache` leaves `IImageIterator`; only the iterator reads its cache. The `clearCache` flag of `ReloadAsync` stays, for the reshows of a Side-by-Side pair.
- Crop still ignores effects, and Optimize is still lossless.
- Batch resize writes files that are not shown and stays outside the module.
- Undo/Redo is a TODO at the backup step.
- Known gap: an over-itself write of an animated GIF or WebP, a multi-page TIFF or an SVG writes one raster frame, as Save did before; the Recycle Bin copy is the net.
- The Recycle Bin gets a copy for every write over an existing file when the temp folder's drive has a bin, restored into the temp folder. A write can go ahead with no backup, and a replace can leave the original beside the new file; both are logged.
