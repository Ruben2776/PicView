# A Tab's File List Keeps Its File Order

The **File Order** is a **Window Setting**: a `FileOrder` (`PicView.Core/FileSorting`, a field `SortFilesBy` and a direction) in `MainWindowViewModel.WindowSettings.FileOrder`, seeded from the record's `Sorting` group and stored back to it when the window closes, as ADR-0038 says. `FileOrdering` is a `FileOrder` with the platform's name comparison, and it is the one comparison for sort, insert and archive entries: it compares the chosen field, then the name, then the full path (for an archive entry the flat name ordinally, as its file's path in one folder ends, then the entry key), so no two files tie and a sort or an insert puts a file in one place only. Random shuffles in `Sort` and appends in `InsertPosition`. A file the disk cannot read counts as size zero or the earliest time. `ImageIterator.Ordering` is the ordering its list was made with, set by `Initialize(files, index, ordering)` and replaced by `Resort`; `Insert`, `InsertMissing` and `Move` place files by it, so a created or renamed file lands where a sort would put it. `TabViewModel.CurrentOrdering()` is the ordering a tab lists with now: its window's File Order, or the record's for a tab or tab overview with no window. A tab follows the window's File Order through `CurrentWindowSettings`, so a sort in the menu sets the window's order (`TabOverviewViewModel.SortAsync`) and every tab of that window re-sorts its own files, through `TabViewModel.ResortAsync` and `ImageIterator.Resort`, in memory and off the caller's thread, keeping the Shown File and starting no Load. Asked again while it runs, a re-sort runs once more when it ends, so any number of changes end in the latest order. After every list a Load gives the tab, `FollowListedOrder` compares the list's order with the window's and re-sorts when they differ, so a sort, or a tab moved to another window with another order, while the Load was listing cannot leave the tab in the old order. A Load given ready-made files carries the ordering they were listed with (`LoadOptions.ListedWith`), and the tab keeps that, not its own, until `FollowListedOrder` has checked it. `FileAndDirectoryNavigator` is given a tab's ordering on every call and sorts directories by name with it. An archive's pages are ordered from what the archive says of each entry, before any is extracted (`ArchiveEntryOrderKey`: name, key, size, modified time), by the same `FileOrdering`: the start page and the extraction order follow it, Random shuffles the entries once when the archive is prepared, and the archive structure is respected only when the order is by name. Each page is stamped, on the open file handle, with its entry's modified time as its creation, last write and last access time, so the tab's own list, sorted by any date, keeps the entries' order. An entry with no time (a zero date, which reads as 1980 or earlier) is stamped with a fixed early date, so those files tie and fall back to the name, as their keys do. With Side-by-Side on, a re-sort shows the pair again the way a Side-by-Side toggle does (`ReloadAsync` without clearing the cache), which can briefly enter the Loading Title Phase while a partner that is not cached decodes. A tab showing a Single Image re-sorts its list and shows nothing again. `WindowSettingRecordReadsTests` fails on any read of the record's `Sorting` group, apart from `IncludeSubDirectories`, outside `WindowSettings`, `FileOrder`, `AppSettings` and `SettingsManager`; a tab or tab overview with no window reads it through `FileOrder.FromAppSettings`.

Before this, four defects, which the architecture review traced to the order being no one's:
- Sorted by extension, size or a date, a created or renamed file landed in the middle of a run of equal files, because the insert had no tie-break. Extension was sorted with the culture's comparison but inserted with `OrdinalIgnoreCase`, so even a run that was all one extension disagreed with itself.
- Changing the sort re-sorted only the active tab of the window the user was in. Every other tab and every other window kept the old order and binary-searched it with the new one, which put inserted files in the wrong place.
- An archive's pages picked their start page and their extraction order by name, whatever the sort, so the pages were extracted in an order the tab's list did not have.
- `FileAndDirectoryNavigator` compared a path to the comparer delegate, so Next Archive past the last archive of a folder searched from the first sibling.

## Considered Options

- **The File Order per tab.** A tab would not need to follow its window. But the menu's check marks and the Sort items act on a window, the user expects the Sort of a window to apply to its tabs, and a tab that moves to another window would keep an order the window does not show.
- **Re-list from disk on a sort, as before.** It makes the sort the one place that reads the order, but it starts a Load for a change that only reorders a list in memory, and does not help the insert, which still needs an ordering to place a file in.
- **Thread the comparer through each call, as before.** The list does not remember its own order, so a caller that has the wrong one searches a list with an order it was not sorted in. This is what the second and fourth defects were.

## Consequences

- Under Random, an inserted file is appended and a renamed file keeps its index. A Random sort shuffles again each time the item is chosen, and a re-sort to Random from another order shuffles once.
- A re-sort is in memory and starts no Load. The gallery hears it as one Listed change from `Resort` (ADR-0010).
- An Archive Opening in progress keeps extracting in its original order while its listed pages re-sort. Under Random, pages extracted later are appended. Stepping to the next archive in a folder shuffles the folder again on each call, as before.
- On a machine that updates last-access time on read, a later sort by last access can move pages that were viewed, since the stamp is only the first value.
- The list a tab gets for any archive is one `FileOrdering` reproduces alone, so a re-sort to another order and back ends where the archive opened. Every entry's flat file name is given when the archive is prepared (`AssignFlatNames`), and the entries are ordered by those names: entries that share a name, such as `v1/001.jpg` and `v2/001.jpg` with the folders left out, take the `_1`, `_2` suffixes in the keys' ordinal order, whichever page is extracted first, so descending or opened at a later entry the order on disk agrees with the order of the keys. An archive that local software extracts whole (`.7z`, `.cb7`) is laid out flat in its folder under the same names (`LayOutFlat`), its folders in the names when the structure rule is on and the order is by name (`IsRespectingStructure`), as a zip's are, and is then sorted by the `FileOrdering` like any folder; a page's entry is still the path local software wrote it at, so the view history of earlier versions still finds it. Before this, such an archive with folders was listed in folder order while its list was stamped Name, and a re-sort interleaved its volumes until it was opened again. What local software extracts that is not a supported file is deleted with its folders.
- A foldered archive's pages are ordered by their flat names, so folders whose names are a prefix of another's (`Volume 1` and `Volume 1 - Bonus`; `Vol 1` and `Vol 1 (color)`) can come out in another order than comparing folder by folder gives, and one folder's pages can be split around another's. Zips already behaved this way; `.7z` and `.cb7` now do too.
- An archive opened under another order and then re-sorted to Name keeps the plain or suffixed names it was extracted under, without its folders, so its volumes interleave until it is opened again. A re-sort to another order and back still ends where it opened.
- Pages with the same name in different folders take their `_1`, `_2` suffixes in the keys' ordinal order, fixed per archive, so with the folders left out of the names `Volume 10`'s copy of a page name comes before `Volume 2`'s.
- A page that cannot be laid out flat, such as one whose flat name is too long for the file system, is left out, and the rest of the archive opens, as a page that fails to extract is. What is left of local software's tree is deleted as far as it can be; a file another process holds is left for the extraction folder's cleanup.
- `.7z` and `.cb7` pages in folders now show the same flat names as a zip's pages, in the title bar, the gallery and the save-as defaults. The view history and Last File still record the archive and the entry.
- Choosing the order a window has already does nothing, apart from Random, which shuffles again. A re-sort compares the sizes and dates each `FileInfo` cached when it was first read (at listing, for a listed folder), so a file copied into a folder sorted by size is placed by the size it had when its Created event came, and stays there until the folder is listed again.
- `Resort` sorts again while the list keeps changing, so during an Archive Opening that inserts pages faster than a sort ends, the re-sort, and the sort Action awaiting it, lands once the extraction slows or ends. The inserts meanwhile use the old ordering, which the list is still in, so the result is right.
- `Sorting.IncludeSubDirectories` is still an App Setting, read from the record. The guard test forbids every other read of the record's `Sorting` group outside the four files it names; a new entry needs a reason in the test.
- The sort menu's check marks derive from the window's File Order and are one-way, so they cannot be toggled out of step with it, and the last write time item sorts by last write time, which it did not before.
- A tab, or a tab overview with no window, reads the record's order and follows nothing.
- `FileSortOrder` is gone; `FileOrder` and `FileOrdering` replace it.
- The settings file keeps its shape and its version; no migration.
- Slices 3 and 4 of the Window Settings design (Side-by-Side, looping, Zoom to Fit, scrolling, the interface settings, the background and the gallery's look) are not part of this and are still App Settings.
- Supersedes ADR-0020's "only the active tab relists" as it applies to the sort.
- On Linux a file's creation time cannot be set; the stamp sets its last write time there, and whether a sort by creation time keeps the entries' order depends on whether the runtime reports a birth time. Unverified: Linux is unreleased and was not run.
