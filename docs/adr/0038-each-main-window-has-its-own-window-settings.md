# Each Main Window Has Its Own Window Settings, Stored When It Closes

A **Window Setting** is a **Setting** that belongs to one **Main Window**: its value lives in that window's `MainWindowViewModel.WindowSettings`, a `WindowSettings` in `PicView.Core/ViewModels`, and changing it in one window changes nothing in another. After this slice they are the **Window Mode** and **AutoFit** (kept on `WindowModeState`, with `WindowModeState.Remembered` as what is stored), top most (`WindowSettings.IsTopMost`), **Stay Centered** (`WindowSettings.IsStayingCentered`), and the window's last Normal size and position (`WindowSettings.Bounds`, a `NormalBounds`). Every other Setting is an **App Setting** and behaves as ADR-0020 and ADR-0034 say. A window's `WindowSettings` is made before its `WindowTabs`, seeded when the window is made and never again: `WindowSettings.FromRecord` reads the settings record at App Start, and `WindowSettings.CopyFor` copies the opener's values, in the opener's current mode, for a window opened from another Main Window (`OpenNewAsync`) or for a dragged-out tab (`OpenForMovedTabAsync`, from the window the tab came from). A window opened while PicView runs still never starts fullscreen. Nothing writes a Window Setting to the record when it changes. `WindowSettings.Store` writes them only when the window closes: `MainWindowLifecycle.CloseAsync` calls `MainWindowLifecycle.StoreWindowSettings` before the save it already runs, and `AppLifecycle.ShutdownAsync` calls it for the most recently active Main Window, so the last window to close decides what is stored, and at a quit, a restart or an update with several windows open, the most recently active one does. While a window is open the record is stale for every Window Setting, so a follower or reader takes the window's published value, never the record. `WindowSettingRecordReadsTests` scans the sources and fails on any read of `WindowProperties` other than the seed, the store, and the two App Settings that stay in it, `Margin` and `EscLeavesFullscreen`, apart from a short list of files that read a tool window's own remembered placement. The Settings window belongs to no Main Window, so its top most and Stay Centered controls bind through `MainWindows.ActiveWindow`; `CloseAsync` points `ActiveWindow` at an open window when the active one closes. A tab publishes the settings of the window it is in as `TabViewModel.CurrentWindowSettings`; `TabOverviewViewModel` calls `TabViewModel.FollowWindow` in `Adopt` and for a first tab, after the tab's window is set, so a tab that moves to another window follows that window's settings from then on. Nothing follows `CurrentWindowSettings` yet. Slices 2 to 4 of the Window Settings design move the File Order, Side-by-Side, looping, Zoom to Fit, scrolling, the interface settings, the background and the gallery's look under the same rule; until they land, those are still App Settings.

Before this, every Setting was app-wide. `WindowModeSwitcher.Change` wrote Fullscreen, Maximized and AutoFit to the record and saved on every change, and the Window Mode that a new window started in was the last one chosen in any window. `WindowFunctions.SetAutoFitInEveryWindow` turned AutoFit on or off in every Main Window, so one window's toggle changed all of them. `GlobalSettingsViewModel.IsTopMost` wrote through, and every Main Window followed it. Stay Centered was a Settings window checkbox that wrote the record. `OpenNewAsync` saved its opener's size and position into the record so that the new window could read them back from it, which made the record a hand-over channel between windows.

## Considered Options

- **One copy of `GlobalSettingsViewModel` and `GallerySharedSettingsViewModel` per window.** Binding paths would stay, so the diff is smaller. But each copy also carries the App Settings, which would then have to be kept the same across windows: the mirroring ADR-0020 removed.
- **A plain copy of the settings record per window, passed to readers.** Deep Core readers would take a parameter. But nothing would publish a change, so menus, the fitter and tabs would need hand-written pokes again, and ADR-0015, ADR-0017 and ADR-0026 depend on followers subscribing.
- **Keep writing on change, as before, and let the last change win.** The record then holds whatever was changed last in any window, so a Window Setting leaks from one window into the next one opened, and every window that follows the record has to be told. It also keeps the every-window loops.

## Consequences

- A crash loses the session's Window Setting changes. App Settings still save at once.
- The record can hold one window's size with another window's mode. A window that closes fullscreen, maximized or minimized keeps the last Normal bounds it captured, so the stored size and position are those of the last Normal capture, while the mode flags come from the closing window. A window moved by hand and then maximized or minimized by the operating system keeps the bounds from its last capture. A window captures its Normal bounds when it leaves Normal mode (`WindowModeSwitcher.Change`), when it opens a new window through `OpenNewAsync`, and when it closes (`WindowFunctions.RememberBounds`).
- `WindowModeSwitcher` no longer writes the record or saves. A resize by hand turns AutoFit off in that window only. The `AutoFitWindow` Action toggles AutoFit in its own window, `NormalWindow` turns it off in its own window, and `SetTopMost` toggles top most in its own window. `SetAutoFitInEveryWindow` and `ToggleAutoFit` are deleted.
- `OpenNewAsync` takes the opener's size and position from the opener, through `CopyFor`, not through the record. A window opened with no opener, as while only Batch Resize is open, is seeded from the record.
- The Settings window shows and edits the Active Main Window. Stay Centered binds two-way, which ADR-0020 allows where no Action writes the setting; top most runs its Action.
- `GlobalSettingsViewModel` publishes thirteen settings now. `InitializeActionSettings` starts thirteen.
- `MainWindowLifecycle.CloseAsync` disposes the window's `WindowSettings`.
- A window's `WindowSettings` is disposed when the window closes. After that, reading still works, but setting a value or subscribing throws `ObjectDisposedException`, so a follower that switches on a tab's `CurrentWindowSettings` must not subscribe to a closed window's object.
- A tab moved out into a new window publishes that window's settings from the `TabOverviewViewModel` constructor, before the tab is in the collection and before views and hookups are attached, unlike `Adopt`, which publishes after attach. Nothing follows `CurrentWindowSettings` yet; the first follower (the next slice) must move that publish to after attach or tolerate it.
- Two trackers stay, as before: seeding and the Settings window use `MainWindows.ActiveWindow`; storing at a multi-window App Shutdown uses `MostRecentlyActive`.
- The settings file keeps its shape and its version; no migration.
- Supersedes ADR-0006's "the settings only remember the mode a new window starts in", ADR-0007's account of what a closing window stores, ADR-0020's "every Main Window follows top most; the setting is app-wide" and its count of fourteen, ADR-0022's `OpenNewAsync` saving its opener's size and position, and ADR-0034's fourteen in `InitializeActionSettings`.
- Updated by ADR-0039: the File Order joined the Window Settings, and the first tab's `FollowWindow` now runs after the tab is in the window's tabs, so a follower finds it there.
- Superseded in part by ADR-0040: nine more Settings are Window Settings (Side-by-Side, looping, Zoom to Fit, scrolling, the three interface settings and the image background), so `GlobalSettingsViewModel` publishes five settings, not thirteen, and those nine are no longer App Settings.
- Superseded in part by ADR-0041: the gallery's look, the dock edge and the start-docked choice are Window Settings in `WindowSettings.Gallery`, so no slice of the design is left and every Setting its table lists is a Window Setting.
