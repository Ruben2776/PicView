# PicView Runs as One Process; a Later Start Hands Its Source Over

A PicView process that starts while another is running hands its **Source** over to the running one and exits before it makes a window. The running PicView opens the Source: in the **Active Main Window** when open in same window is on, and in a new **Main Window** when it is off. A start without a Source opens a new Main Window with a **Fresh Tab** when the setting is off, and only brings the Active Main Window to the front when it is on. This runs first thing in `Program.Main` (`SingleProcess.HandOverAtStart`, in `PicView.Core/ProcessHandling`), before Avalonia and the settings load, so the process that exits costs no **App Start**. The running PicView's side is `AppLifecycle.OpenHandOverAsync`, and what it does is decided by `HandOverReceipt.Respond` in Core.

Before this, a second start was a second process unless open in same window was on, and PicView started more processes itself to get more windows: for each extra file dropped on a window, and for a later launch file on macOS. Each process loaded the settings, the Keymap, file history and favorites itself and overwrote them when it closed, so the processes lost each other's file history (ADR-0007 already said keeping several processes in sync is not a goal). The old pipe in `IPC.cs` ran only while open in same window was on, never answered, and dropped the file when the running PicView had no window.

How it works:

- **The pipe is the only test of whether a PicView is running.** A start tries the hand-over once without waiting, which fails at once when no pipe exists, so a start with no other PicView running pays one failed connect. When nothing takes it, the process starts listening and runs App Start. A process that cannot listen, because another one began listening in between, as when several files are opened at once, hands over once more, patiently, to that one.
- **Only one PicView listens.** On Windows the pipe decides it: only one process can hold it (`PipeOptions.FirstPipeInstance`). Elsewhere the pipe is a socket file, and making one removes the file that is there, a listening PicView's included, and so does closing one. So there the listener is the process that holds a per-user lock file locked, and it holds it until the process ends, since its closing socket would otherwise take a newer listener's file with it. The system lets go of the lock however the process ends.
- **A hand-over is three lines, and counts only when it is confirmed.** The starting PicView sends `new` or `open <Source>`; the running one answers `ready` or `refused` from a pool thread, whatever its windows are doing; the starting one sends `confirmed` and exits. The running PicView opens the Source only when it reads `confirmed`. No answer in 1.5 seconds, a refusal, or any pipe error, and the new process starts normally as its own process, and since it never confirmed, the running one opens nothing: the Source opens once, never twice and never nowhere. A process that started on its own keeps asking to be the listener for half a minute.
- **Once confirmed, the Source is the running PicView's to find a place for**, because the process that sent it is gone. If **App Shutdown** begins before it is opened, whether it was still held for App Start, waiting for the UI thread, or confirmed after the listener stopped, App Shutdown starts a new PicView process for it after saving and before the process ends.
- **The confirmation gets far longer than the answer.** The starting PicView waits 1.5 seconds for `ready`; the running one then waits up to 30 seconds for `confirmed`, so a confirmation from a PicView that is slow but alive is still read. One that died closes its pipe, which ends the wait at once.
- **A hand-over always leaves a window to see.** A minimized Active Main Window is shown again before it is brought to the front, in the **Window Mode** it had before it was minimized, through `WindowModeSwitcher.LeaveMinimized` (ADR-0006). A new Main Window opened from a minimized one opens where the last Main Window was remembered, not at the minimized window's size or place, and the minimized one stays as the user left it.
- **App Shutdown stops the listener first.** A PicView that is exiting refuses, so a PicView started from then on runs its own App Start.
- **A restarted PicView hands nothing over.** Restarting and resetting the settings start the new process with `--own-process`, which is not a Source. Without it, a restart from a PicView that is not the listener, one that started on its own after a failed hand-over, would be taken by the listening PicView, which would then also write its own settings over a reset. Installing an update starts no PicView itself.
- **Hand-overs that arrive during App Start are held** until the first Main Window is there, and open after it.
- **The pipe is per user**, and on Windows per sign-in session, and only the same user can connect. A Debug build has its own pipe, so a PicView under development and an installed one leave each other alone.
- **On Windows the new process passes on its right to take the foreground** to the running one before it sends the Source, since Windows only lets the process the user just started bring a window to the front.
- **A file or folder given relative to the folder the new process started in** is handed over with its full path.
- **A Source with a line break**, which a file name may have outside Windows, cannot go in a one-line message: the PicView started with it starts normally, as its own process.
- **macOS takes no part in the pipe**: the system already brings a later start to the running app, and `OpenLaunchFileAsync` opens its file the same way a hand-over is opened.
- **A file-association start** (`associate:`) is left out: it is an elevated process that does its work and exits.

## Considered Options

- **Ask the process list** (`Process.GetProcessesByName`), as before. It costs every start a walk through all processes, it cannot tell a PicView that is exiting from one that will answer, and it finds other users' PicViews.
- **A named mutex to decide who is first, on every platform.** A mutex held by a process that is exiting says a PicView is running when none will answer, so the pipe would have to be asked anyway. Where the pipe cannot decide who listens, a lock file does that one job and nothing else.
- **Two lines: answer `taken` and open at once.** A starting PicView that gave up waiting a moment before the answer was written then opened the Source itself as well. The confirmation makes the starting PicView the one that decides, while it is still there to act on its decision.
- **Hand over inside App Start**, where the old check was. The process that exits would load Avalonia and the settings first, and could show a window before it is gone.
- **Open a handed-over Source in the startup order of ADR-0005**, sizing the new window to the image before it is shown. `QuickLoad` is written for the first window of the process. The new window opens as any new window does, on top of the Active Main Window at its size, says Loading from the start, and loads through Core.
- **A new Main Window for a start without a Source even when open in same window is on.** With that setting the user has asked for one window; starting PicView again brings it forward.
- **Refuse while no Main Window is open**, as when only Batch Resize is. The new process would be a second PicView next to Batch Resize. A new Main Window opens in the running one instead.

## Consequences

- One process holds the settings, the Keymap, file history and favorites, so nothing overwrites them from another process, except a process that started on its own after a failed hand-over.
- Extra files dropped on a Main Window, and a later launch file with open in same window off, open in new Main Windows of the same process. Only restarting, resetting the settings, installing an update, and a hand-over that App Shutdown overtook start a new process.
- `MainWindowLifecycle.OpenNewAsync` can be called from any thread and takes the Source the new window shows.
- Open in same window no longer has a follower in `AppLifecycle` (ADR-0020, ADR-0034): each hand-over reads the setting when it arrives, so toggling it takes effect on the next start.
- **App Start** runs once per process as before (ADR-0007), and now also once for however many times the user starts PicView while it runs.
- A crash takes every Main Window with it, where separate processes lost one. A Source confirmed just before a crash is lost with it.
- Three windows a few milliseconds wide are known and accepted, since closing them would take machinery out of proportion to them:
  - A hand-over answered `ready` just before App Shutdown, whose `confirmed` arrives after the listener stopped, is started as a new process at once, from a pool thread, before the settings are saved. That process may read the settings from before the save, and if the process ends first, the Source is lost.
  - During a settings reset such a process is an ordinary start. If it runs its own App Start around the reset, it can write its settings over it.
  - A restart with a hand-over still unopened starts two processes, the restarted PicView and the one for the Source, which race to be the listener. Usually the second hands over to the first; otherwise there are two PicViews.
- Two PicViews of different versions for the same user hand over to each other, so the three lines have to stay readable by both.
- The rules are tested in plain xUnit over a real pipe with a name of its own, the start of a process through an overload of `HandOverAtStart` that takes the pipe, folder and waits, and the receiving side in headless tests. The lock file is tested on Windows, where the same code runs against the same kind of lock; nothing has been run on Linux or macOS, so the socket and the lock there are untested.
