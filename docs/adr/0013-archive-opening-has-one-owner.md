# An Archive Opening Has One Owner, and Its Pages Reach the List From It

Each **Tab** holds one module, `ArchiveOpenings` in Core, that owns every **Archive Opening** of the tab: preparing the archive, extracting the start page and up to nine after it, extracting the rest in batches of ten in the background with a progress text, inserting each page into the tab's file list as its write completes, and ending finished or stopped. The iterator asks it one question when Next runs past the last listed page: whether the opening is extracting, finished or stopped. Its state is read-only outside it, and the UI's extracting flag and progress text derive from it. Page identity (which archive and entry a shown file came from) and the renames stay on its interface, since View History recording (ADR-0012) and `FileRenames` need them; the naming, ordering and folder mechanics of `ArchiveExtractionService` become its implementation.

Before this, the opening was spread over four files: `NavigationService` ran a four-step protocol twice (once per value of the `AlwaysUncompressEntireArchive` setting), wrote the tab's UI-bound `IsArchiveExtracting` at five sites and lowered it from a static `EndExtraction`; `ArchiveExtractionService` exported tokens, folders and counters that only `NavigationService` used; `ImageIterator` read the UI flag before the list, in a documented order, and separately asked whether the latest extraction was stopped; and pages reached the list by two routes, the folder watcher and an end-of-extraction sweep for the pages the watcher had not listed yet. Twenty of the eighty commits before this touched that one path, and the tests set the flag by hand eleven times.

## Considered Options

- **Pages reach the list through the folder watcher, with a sweep at the end**, as before: the watcher handles a folder's events one at a time and can be behind, so the end of the extraction had to list what it missed under the files lock, and a waiting Next had to read the flag before the list. With the owner inserting each page as it is written, a page is listed before the owner can say the extraction ended, and the watcher skips extraction folders.
- **A module per opening with no per-tab parent**: an opening has to know whether a newer one started, which folders are not cleaned up yet, and which opening a shown page belongs to. Those are the tab's facts, so the per-tab module hands out openings.
- **The UI flag as the synchronization flag**, as before: anything could write it, and tests did. The state now has one writer, and the flag is derived.
- **Keeping both extraction protocols**: one entry first and the rest one by one with no progress, or ten first and batches of ten with progress. They differed only in batch sizes and progress, and the second was the default. The setting is removed and the second is the only protocol; the side-by-side partner is added to the first batch when it falls outside it.

## Consequences

- `Settings.Navigation.AlwaysUncompressEntireArchive` is gone from the settings, the Settings window, the settings search and every language file. An old settings file still loads, since unknown members are skipped.
- A load takes a mark from `ArchiveOpenings` as it begins and reports which opening is shown once its image shows; the owner deletes the folders of the openings at or before the mark except the shown one. Loads of files, folders and URLs report that none is shown. This is the rule `CleanupOpened` applied at eleven sites, in one place.
- An opening is overtaken when a newer opening starts on the same tab, which it notices itself. A newer load of a file is the tab's load version, which `NavigationService` checks once, after the opening returns its seed and before the seed shows.
- The folder watcher does not watch a folder the tab's `ArchiveOpenings` claims as an extraction folder.
- Writing an entry's stream to its file goes through an entry-writer adapter the owner takes: the app's copies the stream, and a test's can hold a page's write open. `HeldWriteExtraction` and the internal virtual it overrode are gone.
- The startup order of ADR-0005 is unchanged: archives at startup still show the window and then load through Core, now through the owner.
